# Dashboard / Application Logic — How Data Flows Once It Leaves The Model

> **Audience:** supervisor / validator reading this as a validation artifact.
> **Scope:** everything that isn't LLM prompt content — mode-resolution control flow, extraction validation/persistence, weekly aggregation, pattern-chain computation, the daily journal reset, the analysis-corrections system, the memory pipeline's confirmation/retrieval/editing mechanics, and the dashboard/UI surfaces built on top of all of it. What the model is actually *told* — system prompt text, tone rules, the extraction/memory prompt content itself — lives in the companion document, `docs/ai-prompts.md`, not here.

> **Last updated:** 2026-08-18.

## 1. Mode resolution — the ceiling rule as implemented

```
crisis (keyword match) → witness / engage (intent pick) → witness (default, no pick)
```

(`hold_back` omitted from the live chain — its prompt content is kept written in `ai-prompts.md` §2, just not reachable by any code path yet.)

1. `looksLikeCrisis($entry->body)` scans the lowercased body against the keyword list (content: `ai-prompts.md` §4). Match → `crisis`, overriding everything else.
2. Look up `$entry->dailyIntent?->pick`.
3. Map through `PICK_TO_MODE` (`engage`/`witness` only). No match/no pick → `witness`.

**Same-day memory:** before generating a reply, `CoachService::recentHistory()` pulls up to the last 6 same-day entry/coach-message pairs and feeds them into the LLM call as real conversation turns. This was added after testing showed replies to meta-comments ("that's rude", "who are you") were nonsensical — the coach had zero memory of its own prior message and reflected the complaint itself back as if it were new journal content.

**The model was never told what to do when asked about memory it doesn't have (fixed 2026-08-12).** A real question — "what about what we talked about in the past week" — landed on a coach that has *only* same-day history and no instruction covering this case at all, so its behavior on a memory question outside that window was completely unspecified. The shared prompt now has an explicit rule (content in `ai-prompts.md` §3's memory-honesty bullet): if asked about a previous day or anything needing memory beyond what's in the conversation history it was actually given, say plainly that only today is visible, rather than guessing.

**Still missing from the spec:**

| Signal | Spec requires | Current status |
|--------|--------------|-----------------|
| LLM classifier call #1 | Structured JSON mode recommendation | Not built — mode is keyword + pick only |
| `theme_streak`, `mood_on_theme`, `self_ref_density` | Trigger hold_back escalation | Not implemented — no longitudinal aggregation layer. This is now the ONLY thing standing between hold_back and being reachable again |
| `analysis_requests` | Anti-binge cap on mode ceiling | Column exists in `daily_intents`, never incremented or checked |
| `notable_entity` as classifier context | Passed to classify step | Extraction resolves it (`notable_entity_id`), but no separate classify step consumes it — only the strategy-hint lookup uses it |

## 2. Coach reliability mechanics

**Output-side guard.** `sanitizeReply()` runs on every non-empty LLM response before it's saved: discards it if it contains any of the prompt's own section markers (a leak, via `LEAK_MARKERS`), matches one of `BANNED_PHRASE_PATTERNS`, or exceeds 800 characters (the model badly ignoring the length instruction). This is a backstop, not a substitute for the input-side prompt defenses (`ai-prompts.md` §3) — if it discards a reply, a fallback line still returns something rather than silence.

**Input-side injection detection.** `looksLikeInjection()` is the same shape as `looksLikeCrisis()` — a keyword net over the lowercased entry body (a flat `str_contains` list plus, since 2026-08-14, a small regex pass for phrasings the flat list can't flex to), checked in `generate()` before the messages array is built. A match triggers the reinforcement-wrapper prompt content described in `ai-prompts.md` §3, and logs a warning with the entry ID for later review. Over-triggers on purpose, same posture as the crisis net.

**Output-side compliance check — now wired in (was a gap, resolved 2026-08-14).** `CoachService::INJECTION_COMPLIANCE_MARKERS` — phrases indicating a reply either leaked something about its own instructions or complied with an injected role-override — is checked inside `sanitizeReply()` the same way `LEAK_MARKERS` is: any match discards the reply (logged, then a real retry runs, same as any other `sanitizeReply()` discard). Previously declared but never actually checked; a real adversarial test transcript proved the gap mattered in practice (see `ai-prompts.md` §3 and `memory.md` §10 for the transcript and what it found) before this was fixed.

**Both keyword lists were broadened from that same real transcript, not from guessing at hypothetical phrasings.** The list now also catches: paraphrased prompt leaks that avoid literal quoting ("the previous instructions were a set of guidelines that outlined how I should respond..."), explicit role-override acknowledgments ("I acknowledge that my previous instructions are no longer valid..."), and — a distinct failure mode from prompt leaking — the model complying with "tell me everything you know about the user" by fabricating a demographic profile (age, nationality, family, personality inferred from writing style and purchases mentioned). That third case isn't really an "injection compliance" issue in the traditional sense, but it's exactly the kind of thing this app's core "extraction, not inference" principle exists to prevent, applied to the coach's free-text replies instead of just the extraction schema — so it's caught by the same output-side mechanism rather than left unhandled.

**Banned-phrase enforcement was reverted to logging-only.** It was discarding real, otherwise-good replies too often — a real reply with one clinical-sounding phrase was judged better than the generic fallback ack replacing it. The prompt-level ban (`ai-prompts.md` §3) is the only active defense; violations are now observability only (logged for tuning signal, never block a save).

**`GenerateCoachMessageJob`'s declared `tries=2` was silently inert (fixed 2026-08-12, real bug found from a user report).** A user got a canned fallback line in response to an ordinary question and asked whether that was a real answer — it wasn't; the actual LLM call had failed. The deeper problem: `CoachService::generate()` previously never threw on any failure — an LLM call failure, a `sanitizeReply()` discard, and a `CoachMessage::create()` DB failure all immediately returned a (fallback or null) result, which the queue counts as success, so the job's declared retry never actually ran. Same silently-inert-retry bug class already fixed for extraction (§3 below) — it had gone unnoticed here until a real user hit it. Fixed the same way: `generate()` now throws on all three failure paths, `GenerateCoachMessageJob::handle()` catches, checks `$this->attempts() >= $this->tries`, and only calls `CoachService::fallbackFor()` (which re-resolves the mode and creates the canned message) on the genuinely last attempt — otherwise it rethrows so Laravel's queue does a real retry with a fresh LLM call. The coach's call timeout was also raised from the 30s default to 45s.

One subtlety this fix had to account for: `handleCrisis()` deliberately never throws on an LLM failure (it already has its own immediate, no-retry fallback — a crisis reply must never be delayed waiting on a retry), so `fallbackFor()` only ever reaches the generic engage/witness canned lines for those two modes; if a crisis entry's `CoachMessage::create()` call itself fails (the one way `fallbackFor()` could still see `mode === 'crisis'`), it uses the crisis acknowledgment + `config('crisis.message')` instead — a crisis entry's last-resort reply must never silently downgrade to the generic fallback line with no resources attached.

## 3. Extraction — validation and persistence mechanics

Runs asynchronously via `ExtractEntryJob`, independent of coach message generation (`GenerateCoachMessageJob`) — both are queued separately off the same entry, so one failing doesn't block the other, and neither blocks the HTTP response to the user. (What the extraction *prompt* actually asks for — the field schema, moment tagging, taxonomy — is `ai-prompts.md` §5; this section is about what happens to the response afterward.)

**Validators tolerate a bare-string item, not just the full object shape (2026-08-12, real bug fix).** Found from a real extraction response: `protective_factors` came back as `["family"]` — a plain string — instead of the requested `{"factor": "family", "impact": ..., "moment": ...}` object, and the old validators required `is_array($item)`, so the entire tag was silently dropped even though `"family"` is a perfectly valid, closed-vocabulary label. A new `rawLabel()` helper now accepts either shape, applied consistently across every field validator. Shape-tolerance fix only, not a taxonomy change — a bare string that doesn't match any allowed enum value still correctly gets dropped.

**Both fixes above only prevent the bug going forward — one already-affected row needed a manual backfill.** The entry that surfaced the bug (`entry_analyses` id 49) had already been extracted and persisted *before* the fix landed. Since `raw_json` preserves the model's literal original output untouched, the fix was applied retroactively by re-running the corrected validation logic against that one row's `raw_json` and writing the recovered values back. Checked against all 49 existing rows first to confirm scope: only this one row had a real data-loss difference.

**Validation is field-level, not all-or-nothing.** The previous version discarded the entire entry — mood, sentiment, entities, everything — if a single field was malformed. `validateAndNormalize()` now checks every top-level key independently; an invalid/missing field is normalized to a safe empty value and recorded in `extraction_issues` (a JSON column persisted alongside the row it describes), but never blocks any other field from saving. Only a response that isn't valid JSON at all still discards the whole entry.

**Stable vs. experimental is a policy label on top of that same mechanism.** `thinking_patterns` is validated more leniently and is expected to come back empty far more often without that being treated as a bug. Everything else is "stable": a validation failure there is logged as a real accuracy signal worth investigating.

**Timeout and retry (the "long entries never get a breakdown" bug).** `storage/logs/laravel.log` showed a real timeout on the extraction call for long, emotionally-rich entries — more emotions/stressors/behaviors, each carrying an evidence quote, needs more completion tokens, which pushed past the shared 30s default. `NvidiaClient::chat()` now accepts a per-call `timeout` option; extraction specifically requests 50s. The bigger issue underneath: `extract()` previously just returned quietly on a failed call, which Laravel's queue counts as a *successful* job — `ExtractEntryJob`'s `tries = 2` never actually retried anything. Both failure paths (no response at all, or a non-JSON response) now throw, so the declared retry genuinely runs.

**On success:** entities are `firstOrCreate`d per `user_id + name + type` (`trigger_status` always starts `unconfirmed`), synced to the entry via pivot, `notable_entity_id` resolved case-insensitively, and — if the user has `>= 5` total analyses and an entity has `>= 3` entries — a valence suggestion may be computed by comparing that entity's positive/negative rate against the user's baseline, surfaced to the user for confirmation (never auto-applied).

**Category suggestion (2026-08-17), a second column entities carry alongside valence, not a replacement for it — redesigned twice the same day from real usage feedback.** User's first ask: *"i want to make the threads you've named into categories positive negative work family ext[c]."* First version: `Entity::CATEGORIES` was a 7-value list including `positive`/`negative` themselves as two of the category options, with a sentiment-rate-vs-baseline fallback when no domain signal was strong enough. Second round of feedback: *"don't label them just positive an negative label them work family hobbies passion study ext ... when i click i'll see the entries positive or negative"* — category dropped `positive`/`negative` entirely and became purely domain-based; valence (untouched, separate column, exactly as it always worked) moved to coloring the *individual thread bubbles* once a category is opened, not to being a category itself.

**Current shape.** `Entity::CATEGORIES` is a fixed 10-value list — `work`, `family`, `hobbies`, `passion`, `study`, `health`, `social`, `finances`, `self`, `other` — populated by `EntryExtractionService::maybeComputeCategorySuggestions()`, gated identically to the valence heuristic above (same `>=5`/`>=3` thresholds, same "suggested, never auto-applied" confirm flow). Domain signal comes from two sources tagged on the entity's entries, tallied together:
1. Stressor `category`/`subcategory` pairs (`ExtractionTaxonomy::STRESSOR_CATEGORIES`) — `work` → `work` (or `study` specifically when the subcategory is `school`), `health` → `health`, `finances` → `finances`, `self` → `self`, `relationships` → `family` when the subcategory is `family`, else `social`. `external` stressors have no confident single-word home in this list and are left out of the tally.
2. Protective-factor tags — `hobbies`/`reading`/`music`/`nature` → `hobbies`, `family` → `family`, `friends` → `social`, `exercise`/`sleep`/`therapy` → `health`, `journaling` → `self`. Needed because stressors alone have no way to signal `hobbies` at all — a thread about something that consistently *helps* is exactly the kind of signal a pure stressor tally would never surface. `faith`/`pets` left unmapped, same conservatism as `external` above.

`passion` has no source in either taxonomy and is therefore never auto-suggested — a real gap (there is currently no manual category-picker UI, only confirm/dismiss of a suggestion), noted rather than papered over with a guess.

**Threshold bug found and fixed the same round: majority-of-signal, not majority-of-entries.** First version required the leading domain to cover `>= 50%` of the entity's total analyzed entries. In practice this was too strict — most entries carry no stressor/protective-factor tag at all (a mundane entry has nothing to map), so a thread like "the deadline" (3 clear `work`-stressor tags across 10 entries, zero *competing* domains) never reached 50% of 10, even though `work` was the only domain signal it ever had. Fixed to require a majority of whatever domain signal actually exists (`topCount / array_sum($domainTally) >= 0.5`) plus a minimum of 2 real mentions, so a single stray tag still can't label an entire thread. Deliberately not an LLM call — same "every trend is computed deterministically in PHP from stored history" principle as valence itself.

**Frontend: the "threads you've named" card is now two levels, not one (`Dashboard.vue`).** The single-level SVG (every confirmed entity in one ring) plus the separate positive/negative/neutral tag lists below it are both gone, replaced by one set of category bubbles — sized by how many threads live in each, colored by cycling the 10 domain labels through the existing `--chart-1..8` categorical palette (2 unavoidable color repeats; `uncategorized` gets `--muted` instead of a chart color so it reads as "not yet sorted," not as an 11th real category). Clicking a category bubble expands it: that bubble becomes a hub, the individual named threads inside it appear as satellite bubbles orbiting it (CSS transitions on `cx`/`cy`/`r`/`opacity`, ~0.45s ease), and every other category bubble dims rather than disappearing. **The individual thread bubbles are colored by valence** (`--positive`/`--negative`, the same variables the app used before any category work existed) — this is the "when i click i'll see the entries positive or negative" half of the redesign. Clicking a thread bubble still opens the exact same detail drawer as before (`openThread()`/`threadPanel`, untouched).

**Two real bugs found from actual usage, both fixed the same round:**
1. **Every pre-existing thread showed up as one giant "uncategorized" bubble.** Root cause: `maybeComputeCategorySuggestions()` (like `maybeComputeValenceSuggestions()` before it) only ever runs as a side effect of processing a *new* entry that mentions the entity — it has no scheduled/background counterpart that re-evaluates entities nobody has journaled about again since the feature shipped. Fixed with a one-time backfill (applied directly via Python since there's no PHP runtime in this environment to run a real Artisan command) replicating the exact heuristic against the live data. **Reusable lesson:** any future suggestion-type feature added to `entities` (or any table with pre-existing rows) needs an explicit backfill step — "only computed on new activity" silently does nothing for history that predates the feature.
2. **When the category taxonomy changed mid-flight, entities that had already been confirmed under the OLD `positive`/`negative` values were stuck with a `category` no longer in `Entity::CATEGORIES`.** Since the frontend's category grouping only iterates the fixed, current category list, those threads would have silently disappeared from every bubble (not even landing in "uncategorized") rather than erroring visibly. Fixed as part of the same backfill pass: any `category`/`category_suggested` value not in the current enum was reset to `null`, then recomputed under the new heuristic. **Reusable lesson:** changing an enum backing an already-populated column needs an explicit migration/backfill for existing values, not just a validation-rule update — an old value silently becomes invisible instead of erroring.

**Third bug, found one round later from a recurring user report — silent PATCH failure across the whole gentle-note flow, not just category (`Dashboard.vue`).** User: *"there is always this bug that keeps on comming back inn gentle note when i click at yes that fits the note doesn't leave when i click again it became uncategorized."* Root cause: `confirmNote()`/`dismissNote()`'s optimistic update was `api.patch(...).finally(reload)` — every one of the 6 note types (`trigger`/`valence`/`category`/`strategy`/`canon_event`/`pattern_correction`), no exceptions — with no `.catch()` anywhere. If the request failed for any reason, the rejection was swallowed silently and `.finally()` still ran the reload, which pulled real server state and overwrote the optimistic update with zero visible feedback — indistinguishable, from the user's side, from "I clicked yes and it undid itself." The concrete trigger here was exactly bug #2 above: a browser tab left open across the taxonomy change still held a `category_suggested` value the updated backend validation now rejected, so every confirm click on that stale tab failed the same way, repeatedly, which is why it read as "keeps on coming back" rather than a one-time glitch. Fixed with a `noteError` ref and a `.catch(onFail)` added before every `.finally()` across both functions — the reload-on-failure behavior is intentionally unchanged (reverting to server truth on a genuine failure is correct), the bug was only that it happened invisibly. A visible line now reads "couldn't save that — try reloading the page." when any of the 6 branches fails. **Reusable lesson:** this class of bug (a stale-loaded browser tab whose in-memory state predates a backend validation change) has now recurred three times this session in different forms (crisis contact placeholder text, crisis auto-navigate, this one) — silent failure handling on optimistic-update endpoints is the generic mitigation, not a per-feature fix, which is why this fix was applied to all 6 note types at once rather than just the one that was reported.

**Temperature:** extraction defaults to the client's low value (~0.1) for repeatable structured output; `max_tokens` raised to 1024 to give the larger schema's output room.

**Retries can now exhaust into a minimal fallback row instead of leaving nothing (2026-08-14, found from a real bug, not anticipated in advance).** A live-database investigation (`entries`, `entry_analyses`, `failed_jobs`, `storage/logs/laravel.log`) traced a real "the AI never analyzed my entries" report to its actual cause: several entries containing prompt-injection-style content made the extraction model drop out of JSON mode entirely — refusing outright or responding conversationally — so `extract()` threw on every attempt, `ExtractEntryJob`'s retries were exhausted, and the entry landed in `failed_jobs` with **no `EntryAnalysis` row created at all**. `ExtractEntryJob` now mirrors `GenerateCoachMessageJob`'s pattern exactly: on the genuinely last attempt, instead of rethrowing into `failed_jobs`, it catches and calls the new `EntryExtractionService::fallbackFor()`, which records a minimal `EntryAnalysis` row — every field null/empty, `extraction_issues` explaining what happened — so the entry stays visible (journal, calendar) and is marked as not analyzed rather than silently missing. The extraction prompt's `SYSTEM SECURITY` line was also strengthened (see `ai-prompts.md` §5) to reduce how often this triggers in the first place. Full writeup, including the six specific entries this happened to and how they were backfilled, is in `memory.md` §10.

**Over-extraction on mundane entries (2026-08-17, real accuracy bug from user-reported feedback on entry 105).** The `frustration`→`anger` alias bug and a general lack of a "what restraint looks like" worked example combined to extract `sadness`, `anger` (should have been `annoyance`), a `self`/`self_doubt` stressor, and an `avoided` behavior from an entry the user described as just an ordinary tired morning with one minor annoyance. Fixed on both sides: the taxonomy fix is `ai-prompts.md` §5's `annoyance` writeup; the prompt now also carries a worked example of restraint on a mundane entry, immediately after the existing "only extract what's supported" instruction. The four corrections the user explicitly named were recorded directly against the live row (`entry_analyses` id 72 / `analysis_corrections` ids 21-24): `emotions/anger` → corrected to `annoyance`, `emotions/sadness` → removed, `stressors/self` → removed, `behaviors/avoided` → removed. `needs/validation` was deliberately left untouched — the user's feedback didn't mention it, so it wasn't assumed to be wrong.

**Known overlap left unresolved:** `strategy_hint`/`strategy_entity` → `Strategy` and the `behaviors[]` field now cover conceptually similar ground — both capture "something the writer did that affected how they felt." Not merged in this pass because doing so properly means also touching `Dashboard.vue`'s confirm UI and `CoachService`'s reference-data injection.

## 4. Weekly aggregation

`WeeklyReflectionController::generateContent()` returns `emotion_breakdown`, `stressor_breakdown`, `protective_factor_breakdown`, `behavior_breakdown`, `need_breakdown`, and `thinking_pattern_breakdown` — each a list (capped at 5) of `{"label": ..., "rate": 0.0-1.0, "share": 0.0-1.0}`, sorted by impact-weighted total, where `rate` is the plain fraction of the week's entries that mentioned that label at all. All six are computed only from entries where `extraction_confidence` is null or `>= 0.4`, so a single ambiguous/sarcastic entry doesn't skew a whole week's read.

**`share` (2026-08-18), added from real usage feedback: "we need an equation that make the statistics more accurate like showing the dominant emotions with a big percentage and not them having the same value."** Before this, the only number a breakdown carried was `rate` — presence, not magnitude: a label counts as `1.0` toward an entry's tally the moment it appears at all, no matter how many times or how intensely. Two emotions each showing up in 2 of a week's 5 entries tied at `rate = 0.4` even if one was a repeated intensity-9 and the other a single passing intensity-2 mention — nothing about which one actually *dominated* the week survived that collapse, which is exactly why the dashboard's bars and dot-fills kept coming out looking flat and same-y regardless of what was really going on. `share` fixes this by reusing the number `tagBreakdown()` already computes for sort order (`$weighted[$label]`, the intensity/impact-weighted total) and turning it into each label's fraction of the *full* weighted total across every label the field produced that week — computed before the top-5 slice, so a real long tail is honestly reflected in the numbers shown rather than padded to sum to 100%. `rate` is left completely untouched (still drives `frequencyWord()`'s "a few times"/"most days" wording, a genuinely different question — *how often across days* — from *how much this dominated*, which the two used to be wrongly conflated into one number for). Only the visual magnitude moved: `Dashboard.vue`'s `breakdownRows()` now sources bar width and dot-fill from `share` (falling back to `rate` for an already-sealed past week whose cached JSON predates this field), and `behaviorPie`'s slice fractions moved from `r.rate` to `r.share` for the identical reason. **Verified against live data**, not just structurally: a Python simulation of the exact algorithm against the real database's emotion data for the current week showed `rate`-based widths of sadness 47% / shame 27% / amusement 33% — amusement reading *wider* than shame despite being the lighter, more scattered signal — while `share`-based widths come out sadness 32% / shame 17% / amusement 13%, a real, legible dominance gradient that lines up with which emotion actually carried the week.

**Corrections are applied before counting.** `WeeklyReflectionController::tagBreakdown()` batch-loads all `AnalysisCorrection` rows for the given analyses and column in one query, then applies them inside the label loop before counting: `removed` → item skipped entirely; `corrected` → the corrected label substituted in place of the original; `confirmed` → label used unchanged. A correction on one entry therefore actually changes what the weekly diagrams show — see §5 for the full correction model.

**Rendered on the dashboard with a deliberate translation layer.** `Dashboard.vue` draws a ring chart from `mood_distribution` plus soft horizontal bar charts for each breakdown above. None of the raw enum values or percentages are shown to the user directly: a `warm()` humanization dictionary translates each backend category into the same plain, caring voice the coach itself uses (`catastrophizing` → "expecting the worst", `work` → "work and deadlines"), and `frequencyWord()` converts `rate` into a plain phrase ("a few times", "most days") instead of printing a percentage anywhere. The bar's width still encodes the real number — the words next to it don't.

## 5. Pattern chains (all-time, not weekly)

`GET /api/patterns` (`PatternController`) answers "why do I keep doing this" without asking the model anything new — it's a re-aggregation of already-extracted per-entry tags. For each **trigger** (a stressor's subcategory, falling back to its category) that's shown up in at least 3 reliable entries, it reports the most common co-occurring **emotion**, **thinking_pattern**, and **behavior** *within those same entries* — each link only included if it clears at least 2 raw co-occurrences. Correction-aware across all four fields.

**Co-occurrence is moment-scoped, not whole-entry.** Before the moment field existed, co-occurrence counted an emotion/thinking_pattern/behavior as linked to a trigger if both simply appeared anywhere in the same entry — wrong when an entry narrates two distinct beats. Occurrences now link only when they share a moment number *when moment data exists*; an occurrence with no moment data (every entry extracted before the moment feature shipped) falls back to the original whole-entry counting. Verified with a regression run comparing old vs. new logic on all currently-extracted analyses: zero differences (expected, since none of them have moment data yet). A separate synthetic test with fabricated two-moment data confirmed the accuracy gain.

**Deliberately all-time, not windowed to the current week** — a single week almost never repeats one trigger often enough for a co-occurrence to mean anything.

**Framing, enforced in the frontend copy:** this is co-occurrence, not causation. Every link is worded as "tends to show up with," never "causes" or "leads to."

**Drill-through — "show me the entries."** `GET /api/patterns/{trigger}` and `GET /api/patterns/{trigger}/{field}/{value}` answer the obvious follow-up a co-occurrence chart raises: *which* entries is this built from? Both routes share the same grouping code as the summary endpoint, so a link's drill-through is guaranteed to return exactly the entries the summary counted for it. On the dashboard, every step in a chain is a button; clicking one opens an inline drawer listing the entries behind it, with the literal evidence quote highlighted for thinking-pattern links.

**Embeddings — scoped, not built.** Would be for "entries like this one" retrieval — given today's entry, surface the 3-5 most semantically similar past entries. SQLite has no native vector type or ANN index; brute-force cosine similarity in PHP is viable at this app's current data volume, not at scale. This scoping note became the design basis for the memory pipeline's retrieval mechanism (§6 below), narrowed to one specific use case rather than the fuller "entries like this" search originally scoped here. Not built as a general entry-search feature.

## 6. Memory pipeline — application logic

*(What the two LLM calls in this pipeline are actually told is `ai-prompts.md` §6. This section is the application-level machinery around them: scoring, persistence, confirmation, retrieval, and the UI.)*

### Why this exists

The coach has same-day memory only (§1's `recentHistory()`) and nothing that carries over day to day. A user asked directly why the coach couldn't answer "what about what we talked about in the past week" — the honest answer was that it architecturally couldn't. This feature is the first real answer to that gap: a second, much narrower memory layer, sitting alongside (not replacing) same-day history.

Three scoping decisions were confirmed before any of this was built:
1. **Suggested by extraction, confirmed by the user** — not fully automatic, not manually flagged. The same shape already used for `strategy_hint` → `Strategy` and entity valence suggestions, applied to a higher-stakes kind of memory: a confirmed memory is meant to be recalled as settled fact across arbitrarily many future entries.
2. **Semantic embeddings for retrieval**, not just entity/keyword matching — the first real implementation of §5's embeddings scoping note, narrowed to one specific use case.
3. **A visible "what me remembers" page** — persistent, indefinitely-retained personal data the app now carries forward and can quote back to the user unprompted, inspectable and reversible without needing to ask, same as corrections and strategies.

### The composite gate — the application's own scoring, not just the model's

`EntryExtractionService::MIN_MEMORY_SCORE` (currently `0.35`) is the app-level decision the two-stage design calls for: Stage 2's `keep === true` is necessary but not sufficient — its three scores are also multiplied into a composite (`importance × stability × confidence`) and a candidate only becomes a suggestion if that composite clears the threshold too. Deliberately conjunctive (multiplication, not an average): a candidate that's important but unstable, or confidently explicit but low-importance, shouldn't turn into a "should I remember this?" prompt just because one axis scored high. Three scores of roughly 0.7 each clear the bar (~0.34); anything weaker on all three axes doesn't, even with `keep: true`.

`MemoryEvaluatorService` fails closed at every layer independent of this gate: a failed/timed-out call, a non-JSON response, a malformed individual verdict, or a candidate the model's response silently omitted a verdict for — all default to rejected rather than approved or dropped silently.

Candidates that survive both the veto and the composite gate go through a duplicate guard (case-insensitive exact match against existing descriptions, any status) so a fact already confirmed — or already declined once — doesn't resurface as a new suggestion just because it came up again in a later entry. This is a same-text guard, not real cross-entry reinforcement tracking (see §7's limitations table, #27) — Stage 2's "repeated or reinforced" question can only ever be judged from evidence inside the one entry it's looking at.

Surviving candidates become `CanonEvent` rows (table/model name kept for continuity from the original 2026-08-12 design — see the 2026-08-14 migration's docblock) with `status = 'suggested'`, `category` from Stage 1, and `importance`/`stability`/`confidence`/`reason` from Stage 2 — kept on the row so the reason a memory was suggested stays inspectable. **A suggested row is fully inert** — no embedding, not retrievable, not shown to the coach — until a human acts on it.

### Confirmation and editing — `CanonEventController`

`GET /api/canon-events/pending` surfaces the single oldest unreviewed suggestion (oldest-first, so the queue actually empties) for the dashboard's one-at-a-time gentle note. `GET /api/canon-events?status=suggested|confirmed` is the full-list version — `Memories.vue` uses it to show the *entire* pending inbox, not just whatever the dashboard notification happens to be showing right now.

`PATCH /api/canon-events/{id}` accepts `status` (`confirmed`/`dismissed`/`forgotten`), and — since 2026-08-14 — `description`/`category` for editing. Confirming is the one status change with a side effect beyond the status itself: it computes the memory's embedding right there in the request, synchronously, via `NvidiaClient::embed($description, 'passage')`. Deliberately not queued — confirming is a rare, user-initiated click, not a hot path, so one embedding call inline is cheap. Editing the description of an *already-confirmed* memory also re-embeds, since the old vector would otherwise silently describe text that no longer matches what's stored; editing a still-`suggested` row's description does not embed, since nothing is retrievable yet regardless. Best-effort throughout: if an embed call fails, the edit/confirm still saves — visibility never depends on retrieval working (see §7, #24).

`forgotten` is kept distinct from `dismissed`: `dismissed` means a suggestion was declined before it ever became a real memory; `forgotten` means a confirmed, active memory was later removed. Both are non-destructive status changes, not deletes — same convention this app applies to corrections and trigger dismissals.

### Retrieval — embeddings, not full-entry replay

`NvidiaClient::embed(string $text, string $inputType = 'passage'): ?array` hits NVIDIA's `/v1/embeddings` endpoint — a separate endpoint and model from the chat completions used everywhere else, verified against NVIDIA NIM's documented OpenAI-compatible shape before writing the client. `input_type` is not cosmetic: NVIDIA's embedding models are asymmetric — `passage` for stored/indexed text, `query` for search text. Mixing these up doesn't error, it just quietly degrades retrieval, so every call site passes the correct one explicitly. Always best-effort — every failure path returns `null` rather than throwing.

`CanonMemoryService::retrieveRelevant()` is deliberately brute-force, not a vector database: loads a user's `confirmed` + embedded memories and computes cosine similarity in PHP against the current entry's embedding, filters below `MIN_SIMILARITY = 0.35`, returns the top 3. SQLite has no native vector type, and at a personal journal's per-user data volume, a loop-and-rank in PHP is genuinely sufficient.

`CoachService::generate()` computes the current entry's embedding (`input_type: 'query'`) and retrieves relevant memories for both live modes — see `ai-prompts.md` §6 for how they're presented in the prompt once retrieved.

### "What me remembers" — `Memories.vue`

`/memories`, linked from the dashboard header. Two sections (since 2026-08-14): a "waiting for your yes" pending inbox showing every not-yet-reviewed suggestion with confirm/edit/dismiss actions, above the "remembered" list of confirmed memories with their category icon, optional entity tag, confirmation date, and edit/"forget this" actions. Editing is inline — a textarea plus a category dropdown, `PATCH`ed as `description`/`category`. Every mutation is optimistic with revert-on-failure, matching the dashboard's other confirm/dismiss actions.

The dashboard's own gentle-note notification remains the primary "should I remember this?" prompt (oldest suggestion, one at a time) — this page is the durable secondary surface for anything that notification didn't catch. Its copy is category-aware: "you mentioned X — want me to remember that going forward?" only fires for `event`-category suggestions; everything else gets "noticed this: X — want me to remember that about you?"

### Demo data

`DemoDataSeeder` adds two confirmed showcase memory rows, deliberately with **no** embedding — a fake vector would misrepresent what a real embedding call looks like, so seeded rows show up in "what me remembers" for demo purposes but aren't retrievable until re-confirmed against a real embedding call. Documented behavior, not a bug. Both rows default to `category = 'event'` via the schema's column default.

## 8. Monthly dashboard (2026-08-17, user-requested: "i want u to create monthly dashboard")

A separate, always-live page (`/monthly`, `MonthlyDashboard.vue`) rather than a new section bolted onto the existing weekly Dashboard. When asked to choose, the user picked **month-over-month trends** over "the same weekly-style breakdowns, just monthly" — this page is about direction across time, not a single month's snapshot — plus history browsing via month navigation.

**`MonthlyDashboardController::trends()`** (`GET /api/monthly/trends?end_month=YYYY-MM&months=N`) computes a rolling N-month window ending at `end_month` (default and hard ceiling for `end_month`: the current month — there's no browsing into the future). `N` is user-adjustable — see the "customizable window" paragraph below; this paragraph describes the aggregation itself, which is identical regardless of N. For each of the same six tagged fields §4 covers, the top 5 labels are chosen by weighted total across the **whole window**, not re-picked per month — the alternative (top-5-per-month) would let a label pop in and out of the chart purely from re-ranking, which makes a trend line meaningless. Every chosen label then gets a rate for every month in the window: `0.0` if it didn't appear that month, `null` if the month had zero reliable entries at all — the frontend treats these two cases differently (a real zero draws a point on the line; no-data breaks the line rather than implying "definitely didn't happen"). Corrections are applied before counting, same as §4's weekly logic. Direction/delta (`up`/`down`/`stable`/`insufficient_data`) compares the two most recent months that each have at least 2 entries, mirroring the weekly trend calculation's own `< 2` guard and `±0.10` threshold rather than inventing a new one.

**Deliberately its own controller, not a refactor of `WeeklyReflectionController`.** The aggregation shape genuinely differs — a fixed label set tracked across N month buckets, vs. weekly's single-bucket top-N — and sharing code would have meant either bending the already-shipped, working weekly `tagBreakdown()` to serve two shapes, or extracting a shared service and touching stable code for a net-new feature. Same "known overlap, not merged" tradeoff already made for `strategy_hint`/`behaviors[]` (§3) — some duplication accepted on purpose to avoid destabilizing something that already works. Also deliberately **no seal/lock ritual** the way `WeeklyReflectionController::current()` has — that ritual is a once-a-week reveal; this page is for exploratory browsing across past months, so it always computes fresh, the same way `/reflections/live` does.

**Frontend: hand-rolled SVG line charts, one panel per field, `MonthlyDashboard.vue`.** Consistent with the rest of this app (no charting library anywhere — see the weekly mood ring / pie / radar). Each panel shows up to 5 lines (one per top label), plus a legend with a plain-language delta readout ("up 15 points from last month") instead of a raw number-only diff. A null-rate month breaks a line into a separate SVG polyline segment rather than interpolating across a gap that isn't real data.

**Follow-up, same day: per-line color and a customizable window (user feedback: "the css sucks in what you've needed more of and what's been helping and what's weighed on you i want each entrie to have a color also let's make the scope ... customizable like i can zoom and look between 2 months or sth").**

*Categorical color palette, not semantic tone.* The original version colored every line by the same `tone-positive`/`tone-negative`/`tone-accent` convention the weekly showcase uses for bars and pie slices. That works for a single visual element per category, but breaks down for a multi-line chart: every stressor category is `'negative'` and every protective factor is `'positive'`, so *every line in those two panels rendered the exact same color* — the literal cause of the complaint, not just a vague aesthetic miss. Fixed by switching to a categorical palette (`--chart-1` through `--chart-8`, defined per theme alongside the existing `--accent`/`--ochre`/etc.) assigned by each line's rank position within its panel, not by what it means. `--chart-1`/`--chart-2` deliberately reuse the theme's existing accent/ochre so the first two lines in any panel still feel connected to the rest of the app; `--chart-3`..`--chart-8` are new muted hues chosen to stay distinguishable from each other. The semantic tone dictionaries (`EMOTION_TONE` etc. in `../utils/taxonomyDisplay.js`) are unaffected and still used everywhere they were before (Dashboard.vue's bars/pie, EntryAnalysis.vue) — this was a "wrong tool for this chart type" fix, not a reason to remove the tone system itself.

*Customizable window.* `?months=` (validated `[2, 24]`, default 6) replaces the old hardcoded 6-month constant. The response echoes back `window_months` (not just accepting the request param silently) so the frontend's zoom control — four buttons, 2/3/6/12 months — stays in sync with what the server actually used, including the fallback case where the request omits `?months=` entirely. Zooming keeps the current focus month and only changes the window size around it. A wide window (12–24 months) would otherwise crowd every month's x-axis label into an unreadable pile on a fixed-width chart, so the frontend thins labels to roughly 8 evenly-spaced ones once the window grows past that, always keeping the rightmost (focus) month's label regardless of the thinning step — dots and lines still plot every month in the window, only the text labels are thinned.

**Second follow-up, same day: weekly-granularity data points, and the color fix extended to the weekly Dashboard (user feedback: "the diagrams doesn't feel accurate like it's just a ligne i want to see the ups and downs for every ligne and like there will be entries buy week and i want the color entrie chyanges to be on the weekly dashboard").**

*One point per week, not per month.* A single monthly aggregate smooths real week-to-week variation into a flat line — with only 1-2 populated months in this app's live data, a line was often just two dots joined by a straight segment, which reads as "just a line," not a trend. `MonthlyDashboardController::trends()` now buckets by ISO week (Monday-start, matching `WeeklyReflectionController`'s own convention) instead of calendar month. The window itself is still month-denominated — `end_month`, `?months=`, and the 2/3/6/12mo zoom control are unchanged — only the plotted resolution inside that window changed; a "2mo" window now renders ~8-9 weekly points instead of 2 monthly ones. Verified against the live database: a real 2-month window produced entry counts of `[2, 3, 7, 24, 35, 2]` across its populated weeks — genuine, visible variation, not a flat line. The trailing edge is clamped to "now" (not the full calendar month) so a week that hasn't happened yet never shows up as a dangling empty data point. Direction/delta's "usable" threshold dropped from 2 entries to 1 (`MIN_ENTRIES_PER_WEEK_FOR_TREND`) — a week with one journal entry is normal, not the sparse outlier a month with one entry would have been, and keeping the old threshold would have made "insufficient_data" the common case. The response's `months` field was renamed to `weeks` (breaking change to the JSON shape, not a versioned/dual-supported one, since this endpoint has no other consumers yet); axis labels are short week-start dates ("Aug 4") rather than month names, with the existing label-thinning logic doing more work now that a wide window can produce ~50-100 weekly buckets.

*Per-entry color extended to the weekly Dashboard.* The categorical palette fix above was monthly-page-only; the user asked for the same treatment on the original weekly `Dashboard.vue`. Three of its panels had the identical bug the monthly page did — `protectiveRows` was always tone `'positive'`, `needRows` always `'accent'`, and the triggers/stressors panel had `tone-negative` hardcoded directly in the template — so every row in each of those three panels rendered the exact same color. Fixed with the same `--chart-1`..`--chart-8` palette (identical hex values to `MonthlyDashboard.vue`'s copy, so the two pages read as one visual language), assigned by each row's rank position via a new `colorVar` field on `breakdownRows()`'s output and on `triggerRows` (computed separately, added after its own sort+slice so rank order matches color order there too). Deliberately **not** applied to `emotionRows`/`behaviorRows`/`behaviorPie` — those already vary by real per-label tone (`EMOTION_TONE`/`BEHAVIOR_TONE`), which is genuine information (positive vs. negative emotion, self-supportive vs. self-undermining behavior) that a arbitrary categorical color would have thrown away for no reason; those two panels didn't have the "everything's the same color" bug the other three did, so they were left alone.

**Third follow-up, same day: independent zoom per panel (user feedback: "i want a zoom for every case in monthly also").**

Zoom was previously one control for the whole page — a single `windowMonths` driving one `/api/monthly/trends` fetch that all six panels read from. `MonthlyDashboardController::trends()` didn't change at all for this round (it already accepted `?months=` per request); what changed is purely how `MonthlyDashboard.vue` calls it. Each panel (`emotions`, `stressors`, `protective factors`, `behaviors`, `needs`, `thinking patterns`) now carries its own 2/3/6/12mo zoom in a `panelWindows` map, and a `cache` keyed by `months` holds the full multi-field response for that window at the current focus month — panels that happen to share a zoom level read from the same cached response instead of each firing a separate request, so the common case (all six still at the default) costs exactly one fetch, same as before. Changing one panel's zoom fetches only that window if it isn't already cached; switching back to a window already in the cache costs nothing. Month navigation (prev/later) still applies globally — since every cached response was computed for the old focus month, `goPrev`/`goNext` wipe the whole cache and refetch exactly the distinct window sizes still in use across all six panels, no more.

This also removed the old page-level "no entries yet in this window" gate that could hide the *entire* grid behind one message, and the old `v-show="!p.isEmpty"` that silently hid a panel with zero tagged data (which mattered more than it used to — `thinking_pattern_trends` is the field most likely to come back sparse per #35 above, and hiding it entirely would have hidden its zoom control too, defeating the point of giving a sparse panel its own zoom to widen). Every panel now always renders with its own zoom row, showing an inline loading / error / "no entries in this Nmo window" / "nothing tagged here yet, try a wider zoom" state as appropriate, rather than disappearing.

**Verification.** Backend aggregation logic was checked two ways before being trusted: a Python simulation replicating the exact algorithm (correction application, weighting, top-label selection, null-handling) run directly against the live SQLite database, and a separate pure-logic test of the frontend's chart-geometry and month-navigation functions (segment-splitting around nulls, SVG coordinate mapping, delta phrasing, year-boundary month arithmetic) against realistic data shapes. The first follow-up (palette cycling, label-thinning, and window-size clamping across 2/3/6/12/24 months), the second (weekly bucketing against the live database including the future-week clamp, plus cross-page palette-index parity between Dashboard.vue and MonthlyDashboard.vue), and the third (a standalone Node simulation of the cache/fetch/dedup logic, confirming shared zoom levels across panels cost one fetch, a panel moving to a new window costs exactly one more, returning to an already-cached window costs zero, and month-nav refetches exactly the distinct windows still in use) were each verified the same way before being trusted. All rounds passed before the feature was considered done. See #35 above for the one open limitation this surfaced.

## 9. Daily breakdown review (2026-08-18)

User's request, verbatim: *"id like to make the breakdown that the user will unteract with after the daylie discussion like a button save the journal then a notification would u like to see the breakdown and then he sees and choose to correct if the discussion gonna end after 24 hour and the user didn't click save the ai will use the breakdown without the user input automatically."* This bundles a real workflow: an explicit "save" action, an offer to review, an optional correction step, and a timed fallback if the user never engages. Four scope questions were genuinely ambiguous and were confirmed with the user (via direct questions, not assumed) before any of this was built:

1. **Whole day, not per-entry.** One save button, one breakdown, one 24h window per calendar day — matches "after the daily discussion" and how the rest of the app already treats a day as the unit (`DailyIntent`, the journal thread's daily reset).
2. **Non-gating.** Extracted data (emotions/stressors/etc.) is already used immediately everywhere — weekly/monthly charts, pattern chains, coach memory — the instant it's computed; confirming/correcting has never blocked any of that, for valence, category, canon events, or thinking-pattern corrections. This feature follows the identical convention: review is a chance to look and optionally correct, never a gate other code waits on. Concretely, this meant no code in `WeeklyReflectionController`, `MonthlyDashboardController`, `PatternController`, or `CoachService`'s memory retrieval needed to change at all for this feature.
3. **In-app banner, not a real notification.** This app has no push/email/SMS delivery of any kind anywhere in the codebase. "A notification" is an in-app banner shown either immediately after clicking save (same session) or on a later visit — same posture as every other gentle-note prompt in this app (valence/category suggestions, canon-event suggestions, pattern corrections).
4. **24h counts from last activity, not a fixed clock boundary.** The window starts from the day's last entry, not a fixed time like the existing 23:30–00:15 daily-reset window (which is itself client-side-only, see #16 below) — a day that runs late doesn't get cut off mid-review.

### Data model — `daily_reviews`

One row per `(user_id, date)`, created the first time an entry lands that day (`EntryController::store()` now does an `updateOrCreate` bumping `last_activity_at` on every entry, independent of whether the user ever clicks anything — same unconditional-row-creation pattern `DailyIntentController::store()` already uses for picks). Three independent nullable timestamps, not a stored enum: `saved_at` (set by the new "save the journal" action), `reviewed_at` (set when the user actually opens the breakdown drawer), `auto_confirmed_at` (set lazily — see below). `DailyReview::getStatusAttribute()` derives a human status from whichever of the three are set, with `reviewed_at` always taking precedence over `auto_confirmed_at` even if both end up populated — looking at a day late still counts as a real review, not just a "technically auto-confirmed" footnote.

**No push notification exists, so "saved_at gates the banner" is the whole mechanism.** Without an explicit save, nothing offers the review at all — the day just silently ages toward auto-confirm with zero interruption, which is exactly the "if the user didn't click save the ai will use the breakdown without the user input automatically" branch of the request. Clicking save is what puts a day into the "waiting for a look" state in the first place.

**Real bug found from actual usage, same day: the `date` column was originally cast as Eloquent's `'date'` type — this silently broke every second write for a given day.** User report: "couldn't load that day's breakdown — try again in a moment. ,couldn't save — try again in a moment." with no further detail (the frontend's own error handling was itself part of the problem — see below). `storage/logs/laravel.log` had the real answer: a `UNIQUE constraint failed: daily_reviews.user_id, daily_reviews.date` violation, with the failed `INSERT`'s own logged SQL showing `date` as `'2026-08-18 00:00:00'` — a full datetime, not the plain `'2026-08-18'` every call site was written to search for. The `'date'` cast only changes how a value looks in PHP (a Carbon instance) and in JSON serialization; it does **not** change how Eloquent formats the value for SQL storage, which always goes through `$dateFormat` (`'Y-m-d H:i:s'` by default) regardless of cast type. So a row created via `updateOrCreate()`'s create path (e.g. the very first entry of a day bumping `last_activity_at`) got `date` written as a full datetime, while every later `updateOrCreate()` call's *search* array used a plain `'Y-m-d'` string — raw `where()` array conditions never pass through model casts, so the search could never match the row the earlier write had actually produced. Every second write for the same day tried to `INSERT` a "new" row and collided with the unique constraint. **`DailyIntent` — the same one-row-per-user-per-day shape, already working correctly in production — never cast `date` at all**, leaving it a plain string written and searched identically every time; fixed `DailyReview` to match that already-proven pattern instead of casting. The one already-corrupted live row was normalized back to a plain date string, and the one place that read `$review->date` expecting a Carbon object (`pending()`'s `->toDateString()` call) was updated since `date` is now already a plain string. Verified with a lifecycle simulation against a scratch copy of the live database confirming a second `save()` call now updates the existing row instead of colliding, the same way the first verification pass (§ above) had already verified the *happy* path but never a same-day *second* write — the gap in that first round of testing.

**A second, smaller bug found alongside it: every daily-review catch block on the frontend showed one fixed string regardless of what actually failed.** This is exactly the same "silent/generic failure" bug class as §'s gentle-note confirm fix earlier the same day — a real backend error (the UNIQUE constraint violation above) was indistinguishable from a network blip from the UI alone, which is part of why this bug took a log read to actually diagnose instead of being obvious from the user's report. `Journal.vue` now has an `apiErrorMessage()` helper that surfaces the server's actual `{"message": ...}` when there is one, falling back to the generic copy only for a true network-level failure with no response at all.

### The 24h auto-confirm is lazy, not a scheduled sweep

This app has no cron/scheduler running anywhere — the same gap already noted for the daily reset being client-side-only (#16 below). Rather than stand up new scheduler infrastructure for one feature, `DailyReview::maybeAutoConfirm()` mirrors `WeeklyReflectionController::current()`'s existing lazy-unlock pattern: whenever any daily-review endpoint (`pending()` or `show()`) touches a row, it first checks whether `last_activity_at` is ≥24h in the past with no `reviewed_at`/`auto_confirmed_at` yet, and if so sets `auto_confirmed_at` right then. Because review is deliberately non-gating (point 2 above), there's no functional gap in this being lazy — nothing downstream needs `auto_confirmed_at` to flip at exactly the 24h mark, only for it to be true by the time anyone next looks (the pending queue, or the user themself). If the user never opens the app again, the day never gets the status flip at all, but nothing was ever waiting on it either.

### `DailyReviewController`

`GET /api/daily-review/pending` — the oldest day that's been saved but neither reviewed nor auto-confirmed, same "oldest unresolved first" queue shape `CanonEventController::pending()` already established, so the queue actually empties instead of always re-surfacing the newest thing. Lazily auto-confirms every outstanding row for the user before picking the next one, so an aged-out day drops out of the queue the moment anyone asks, even if nobody visited it directly. Powers Journal.vue's banner, and — since it isn't scoped to "today" — also covers a day the user saved but never got around to reviewing before the calendar rolled over, since Journal.vue itself only ever shows the current day's thread.

`GET /api/daily-review/{date}` — the six `*_breakdown` fields (same shape and field names `WeeklyReflectionController` returns: `emotion_breakdown`, `stressor_breakdown`, `protective_factor_breakdown`, `behavior_breakdown`, `need_breakdown`, `thinking_pattern_breakdown`) computed from just that day's reliable entries, via `TagBreakdownService::breakdown()` — the exact same aggregation weekly/monthly already trust, not a reimplementation. `POST /api/daily-review/{date}/save` requires at least one entry that day (422 otherwise — saving an empty day has nothing to review). `POST /api/daily-review/{date}/mark-reviewed` fires when the user opens the drawer — "then he sees" from the user's own description of the flow is treated as the review itself; correcting individual tags inside is optional on top of that. `GET /api/daily-review/{date}/{field}/{value}` is the drill-through — which of that day's entries carry a given label after corrections are resolved, each with its `entry_analysis_id`/`original_value` pair so the frontend can fire the *existing* `POST /api/analysis-corrections` endpoint directly. No new correction mechanism was built — this view only tells you which (analysis, original label) pair a correction should target; the actual correction call is the same one `EntryAnalysis.vue`'s inspector already uses.

### `TagBreakdownService` extraction

`WeeklyReflectionController::tagBreakdown()` (including the `share` field added earlier the same day, §4) was moved into `App\Services\TagBreakdownService::breakdown()` so this feature and the weekly reflection share one implementation instead of two copies that could silently drift apart. Pure extraction — the logic itself is byte-for-byte unchanged, only its location and call sites moved.

### Frontend — `Journal.vue`

A "save the journal" button appears in the intent bar once there's at least one entry that day. On success it optimistically shows the review banner in the same session — "then a notification" from the user's description didn't need to wait for a page reload. The banner also reappears on a later visit (via `checkPendingReview()` on mount) if the user dismissed it with "not now" or never engaged, since dismissal is local-only and doesn't touch `saved_at`/`reviewed_at` server-side. Opening the banner ("see it →") fetches the breakdown into a slide-over drawer, marks the day reviewed (best-effort, not blocking the drawer from opening if it fails), and renders the same six fields Dashboard.vue's weekly panels use, with bar width sourced from `share` (the weighted-dominance fix from §4, not `rate`) for the identical "dominant feelings should look dominant" reason. Clicking a label opens the drill-through list of that day's specific entries; each carries a quick "not quite" (`action: 'removed'`) plus a link to the existing full per-entry inspector (`/analysis/{id}`) for a real re-label — the drawer deliberately doesn't duplicate that page's full "change to X" picker UI.

**Known limitation this introduces:** the review banner only ever surfaces from `Journal.vue`, which is itself scoped to "today." `GET /api/daily-review/pending` is written to not care which day it returns, but nothing currently triggers a check from `Dashboard.vue` or anywhere else — a user who only ever visits the dashboard, never journal, would never see the banner for a day they saved from elsewhere. Not a problem yet (the only place `save` can be triggered from is `Journal.vue` itself), but worth remembering if a save action is ever added to another surface.
