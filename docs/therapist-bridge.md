# Therapist bridge — code-invite linking + crisis chat

> **Audience:** supervisor / validator reading this as a validation artifact.
> **Scope:** the client↔therapist linking mechanism, the crisis-triggered chat thread (2026-08-17), share-to-therapist panel sharing, therapist-assigned tasks, scheduled sessions, and the therapist/client interface split (all 2026-08-18). Self-contained, same pattern as `memory.md` — this is one feature end to end, cross-referenced from `dashboard-logic.md` and `ai-prompts.md` where relevant rather than duplicated into them.
> **For what comes next** (live trend view, pre-session briefs, session log, standardized assessments, collaborative strategies, general messaging): see `therapist-roadmap.md`.
> **Last updated:** 2026-08-19.

---

## 1. Why this exists, and what already existed before it

This app already had real, unused database scaffolding for a "therapist bridge" feature, laid down on day one (2026-08-04) alongside a full design spec (`docs/sujet-journal-ai (1).md` §6, §10, §13): a `users.role` enum (`client`/`therapist`), a polymorphic `shares` table for per-item consent, a `therapist_client` pivot table, a `safety_events` table, and a `preferences.product_mode` enum (`solo`/`bridge`) already captured at onboarding. None of it was wired to any controller or route — the roadmap deliberately deprioritized the full "Therapist Bridge" sprint (see `build-roadmap.md`, `dev-log.md`) and it was never reached.

Rather than building that whole planned feature (a full clinical dashboard with an entity graph — see `dashboard-mockup.md` §4), this round builds a narrower, concrete slice the user asked for directly: a way for a client and therapist to link accounts, and a chat between them specifically anchored to crisis moments. It reuses the existing `users.role` and `therapist_client` scaffolding rather than inventing parallel structures, and leaves the broader per-item `Share`-based dashboard sharing untouched and still unbuilt.

## 2. Linking: code invite, not email

**Decision:** a therapist generates a short code and shows it to their client, who enters it to link. Chosen over an email invite ("code invite might be easier") — it puts the client in control of who they link to, rather than requiring the therapist to already have the client's email on file.

- `users.invite_code` — new nullable, unique string column (migration `2026_08_17_000001_add_invite_code_to_users_table.php`). Only meaningful for `role='therapist'` rows. A therapist has exactly one active code at a time; regenerating just overwrites it, invalidating the old one immediately. No history table, no expiry — not asked for, and this is a low-stakes secret (worst case of a leaked code is an unwanted link request, which either party can undo).
- 8 characters, drawn from `ABCDEFGHJKMNPQRSTUVWXYZ23456789` — visually ambiguous characters (`0`/`O`, `1`/`I`/`L`) excluded, since the code is meant to be read off one screen and typed into another.
- `TherapistLinkController::link()` **replaces** any existing link rather than erroring on a second attempt. A client can only ever have one active therapist link — enforced at the application level, not the database (the `therapist_client` table's `unique(therapist_id, client_id)` constraint alone would technically allow linking to several different therapists). One-at-a-time is what makes "who gets the automatic crisis alert" (§4) unambiguous. The frontend (`MyTherapist.vue`, see §11) confirms before replacing an existing link so this isn't a silent surprise.
- Unlinking is explicit and available to either party (`DELETE /api/therapist/link`). A client's crisis-thread *history* with a former therapist isn't deleted — only new access is cut off, since `CrisisThreadController` always resolves against the *current* link, not a snapshot taken when the thread was created.

**New model:** `TherapistClient` — the first Eloquent model for the `therapist_client` table, which existed since day one with none. Deliberately doesn't touch the table's existing unused `focus_text` column (a private note field from the original design) — out of scope for this round, noted here so it isn't mistaken for dead weight.

## 3. Registration: picking a role

`AuthController::register()` now accepts an optional `role` (`client`|`therapist`, defaults to `client`). `Register.vue` shows a plain two-button choice ("i'm journaling for myself" / "i'm a therapist") instead of a dropdown or hidden default.

A therapist account gets **no `Preference` row** — tone, nudge level, product mode, and theme are all journaling concerns that don't apply. `OnboardingController::store()` now guards against a missing preferences row explicitly (422, "Onboarding does not apply to this account") rather than crashing on a null-object call. The frontend router (`router/index.js`) checks `role` before ever redirecting to onboarding, and separately redirects an authenticated therapist away from any journaling page (`dashboard`, `journal`, `calendar`, `memories`, `monthly`, `entry-analysis`) to `/therapist` instead — a therapist's home is the portal, not an empty journaling UI. As of §11, `/therapist` and the client's equivalent (`/my-therapist`) are two different routes/components, not one shared file, and the guard also bounces each role off the other's route.

## 4. Crisis chat: one persistent thread per link, flags surfaced inline

> **Redesigned same day (2026-08-17), after first-round testing.** The first version anchored a chat thread on each individual `SafetyEvent` — one room per crisis flag. Real usage surfaced the problem immediately: a client with several flags over time ended up with several disconnected rooms instead of one ongoing relationship with their therapist. User feedback: *"we need to automate the procedure for every therapis we only need one conversation just when the crisis happen."* The section below describes the current (redesigned) shape; see git history for the original per-SafetyEvent version if needed.

**The core design choice:** the chat thread is anchored on the `therapist_client` **link** (the ongoing relationship), not on any single `SafetyEvent`. `crisis_messages.therapist_client_id` is the thread's real identity; `crisis_messages.safety_event_id` is now nullable, optional context for which flag (if any) a given message is a direct reply about — most messages don't need one. `SafetyEvent` rows are unchanged in how they're created (`CoachService::handleCrisis()` still writes one on *every* crisis-keyword match, exactly as before) but are now surfaced as an inline timeline of "flag" chips inside the one conversation, interleaved chronologically with the messages, rather than each spawning its own room.

Migration `2026_08_17_000003_add_therapist_client_id_to_crisis_messages_table.php` added the nullable `therapist_client_id` FK, backfilled it for pre-existing rows via a join through `safety_events.user_id` → `therapist_client.client_id`, and relaxed `safety_event_id` from `NOT NULL` to nullable. Applied directly against the live SQLite file (full table rebuild, since SQLite can't alter a `NOT NULL` column to nullable in place) — every pre-existing row was verified byte-identical, and the encrypted `body` values were decrypted and spot-checked afterward to confirm nothing was lost in the rebuild.

**Gentle auto-navigate on a crisis reply.** User: *"the brows to /therapist will be automatic also withe a gentle notication to encourage him to talk to his therapist."* When a journal entry gets back a `mode: 'crisis'` coach reply, `Journal.vue` now shows a calm, non-alarming banner (accent-toned, not red/alarm styling) with copy that differs slightly depending on whether the client currently has a therapist linked, and auto-navigates to `/therapist` after a visible 8-second countdown — cancelable via a "stay here" button at any point, and only ever triggered for the reply to an entry sent in that same session (never retroactively on page load, so reopening the journal on a day with an older crisis-mode reply doesn't repeatedly redirect someone).

**Consent model — deliberately different from `Share`.** The wider therapist-bridge design (§"Consent gates every boundary" in the sujet) gates sharing behind explicit, per-item consent. Crisis visibility does **not** work that way: a therapist can see every crisis thread for a *currently linked* client automatically, the moment `CrisisThreadController::index()` is called — no separate per-event opt-in. This was a direct decision, not a default I picked unilaterally: asked whether crisis alerts should be automatic-once-linked or a separate toggle, the answer was automatic — gating a safety mechanism behind an extra consent click on top of an already-completed link defeats the point of it being fast. **Linking via the invite code is the consent for this specific channel.**

**Privacy boundary.** `CrisisThreadController` never loads or returns the triggering `Entry`'s body, anywhere. A `SafetyEvent` existing means a crisis flag fired on *some* entry — it does not mean that entry's journal text crosses to the therapist. Only the fact that a flag happened, and whatever the two people choose to write to each other afterward, is visible. `CrisisMessage.body` is `encrypted`-cast, same treatment as `Entry.body` — this is at least as sensitive.

**What this deliberately does NOT do — read this before assuming "automatic" means "monitored":**
- **No push notification, no email, no SMS.** A therapist only finds out about a new thread by opening `/therapist` and looking. This is the same "always live, check when you check" pattern as every other dashboard in this app (`WeeklyReflectionController::live()`, `MonthlyDashboardController::trends()`) — but for a *safety* feature, that pattern has real teeth: nothing here guarantees a therapist sees a flag in any particular timeframe. If a genuine notification/paging system is wanted later, that's new infrastructure (queued jobs, mail, possibly SMS) — not built.
- **The existing immediate crisis-resource response is untouched and remains the only guaranteed-immediate thing.** `CoachService::handleCrisis()` still shows the `config/crisis.php` resource message to every user the moment a flag fires, regardless of role, link status, or whether a therapist ever opens the thread. The crisis chat is a supplement for linked pairs, never a replacement for it, and nothing about this feature should be read as "the app now has human crisis monitoring."
- **No real-time delivery.** No websockets. Sending a message just re-fetches the thread (`CrisisThread.vue`'s `load()` after `send()`); the other person sees it next time they open or reload the page.
- **`reviewed_at` is an acknowledgment flag, not a resolution state.** `CrisisThreadController::reviewFlag()` is its first real consumer (therapist-only, sets it once per flag). A flag being "seen" doesn't close the thread or stop new messages — the thread has no closed state at all.
- **The auto-navigate in §4 is not a safety guarantee.** It's a nudge toward the right place, not a delivery mechanism — nothing forces the client to stay on `/therapist`, and nothing pages the therapist. It exists purely to lower the friction of finding the conversation, same spirit as everything else in this list.

## 5. API surface

```
GET    /api/therapist/invite-code       therapist — get-or-create current code
POST   /api/therapist/invite-code       therapist — regenerate (invalidates old)
GET    /api/therapist/link              role-aware — client's therapist, or therapist's client list
POST   /api/therapist/link  {code}      client — redeem a code, replacing any existing link
DELETE /api/therapist/link[?client_id]  either — sever a link

GET    /api/crisis-thread[?client_id]              the one thread (client: own; therapist: names a linked client) — includes flags[] + messages[]
POST   /api/crisis-thread/messages  {body,client_id?}  post a message into that thread
PATCH  /api/crisis-thread/flags/{safetyEvent}       therapist-only — mark one flag as seen
```

(Singular `/crisis-thread`, not `/crisis-threads/{id}` — a deliberate rename with the §4 redesign, since there's exactly one thread per link now, not one per flag. `TherapistLinkController::show()`'s therapist branch also now annotates each client row with `unreviewed_flags_count`, via `TherapistClient::unreviewedFlags()`, so the client list itself surfaces who needs attention without opening each thread.)

No Policy layer — every authorization check is inline in the controller (`$user->role`, `TherapistClient::where(...)->exists()`), matching the rest of this app, which has no Policies or custom Middleware anywhere.

## 6. Frontend

`TherapistDashboard.vue` (`/therapist`) and `MyTherapist.vue` (`/my-therapist`) — the hub, one page per role as of §11 (originally one shared `Therapist.vue` file). Therapist side: invite code, a linked-client list/grid (each row showing an `unreviewed` count when nonzero, clicking opens that client's conversation). Client side: link form or current-therapist info plus an "open conversation →" link. Flagged check-ins aren't listed here on either side — that lives in the thread view (§4's redesign), since flags belong inside the one ongoing conversation, not beside it.

`CrisisThread.vue` — the single persistent conversation, reachable at `/therapist/chat` (a client's own thread) or `/therapist/chat?client_id=…` (a therapist opening one specific client's thread, linked from `TherapistDashboard.vue`'s client list). Flags and messages are interleaved into one chronological timeline — a flag renders as a small pill ("flagged check-in — Aug 12", with a "mark seen" action for a therapist on an unreviewed one) sitting right where it happened relative to the conversation, worded plainly rather than alarmingly (no red banners, no siren styling — matches this app's existing restrained crisis-copy tone, e.g. the coach's own crisis acknowledgment is a normal message bubble, not a special UI state).

Both reuse the same theme system (`--paper`/`--surface`/`--ink`/`--muted`/`--accent`/`--line` per theme, dusk/paper/night) as every other page — no new design language introduced. The `Journal.vue` crisis banner (§4) also stays within this palette (`--accent`/`--accent-deep`) rather than introducing an alarm color.

## 7. Verification

No PHP runtime is available in this environment (confirmed: `php` is not on PATH), so — same as every backend change earlier in this project — every new/edited PHP file was checked with a heredoc-aware Python brace/paren/bracket balance checker, sanity-checked against a deliberately broken file first. Every new/edited Vue file was checked with `@vue/compiler-sfc`'s `parse`/`compileScript`/`compileTemplate`. `router/index.js` was checked with `node --check`.

The first-round migrations (§2, §4's original version) were initially only written, not applied — this caused a real "could not load this page" bug (the tables/columns simply didn't exist yet in the live SQLite file). Fixed by applying the equivalent DDL directly via Python's `sqlite3` module and recording the migrations in Laravel's own `migrations` table, so `artisan migrate` will recognize them as already run once a real PHP environment is available. The §4 redesign's migration (`…000003_add_therapist_client_id…`) was applied the same way — but this time as a full table rebuild (SQLite can't `ALTER COLUMN ... DROP NOT NULL` in place), with every pre-existing row checked byte-identical before/after, and the encrypted `crisis_messages.body` values decrypted and spot-checked afterward (via a from-scratch Python port of Laravel's AES-256-CBC + HMAC-SHA256 `'encrypted'` cast) to confirm the rebuild lost nothing.

Demo data (`DemoDataSeeder::seedTherapistBridge()`) was updated to match the redesigned schema — `crisisMessage()` now sets `therapist_client_id` on every message it writes, not just `safety_event_id`. The live demo data itself didn't need reseeding since the migration's backfill already updated the existing rows in place; the seeder change matters for anyone provisioning a fresh install going forward.

Not done: no integration test exercising the actual link → crisis flag → thread → message flow end to end (no test infrastructure was exercised this round, consistent with the rest of this app — `tests/` has no coverage of the other therapist-bridge scaffolding either, per the research that preceded this build).

## 8. Share to therapist (2026-08-18)

**User's request, verbatim:** *"for every diagram... the feelings that showed up, what's been weighing on you.... to have a little button in the upper side to share it to the therapist in monthly too also let's brainstorm based on the competitor what will the therapist part have."*

**What already existed and got reused, rather than a new mechanism.** §1 above notes this app had unused day-one (2026-08-04) scaffolding: a polymorphic `shares` table (`user_id`, `shareable_type`+`shareable_id` morph, `granted_at`, `revoked_at`) and a `Share` Eloquent model, both untouched and empty (0 rows) until this feature. The original design spec (`docs/sujet-journal-ai (1).md`) is explicit that "nothing is shareable without an explicit per-item action" and that sharing must be revocable — exactly what `granted_at`/`revoked_at` already encodes. Rather than inventing a parallel sharing table, this feature adds the one thing that didn't exist yet: something for a `Share` row to point *at*.

A dashboard panel ("the feelings that showed up," "what's been weighing on you," etc.) isn't a stored Eloquent row — it's a computed aggregate, recomputed live every page load from `TagBreakdownService`/`MonthlyDashboardController`. So "share this panel" can't mean a live link the way `CrisisThread`'s always-current resolution works; it means freezing a copy of exactly what's on screen at the moment the client clicks share. `InsightSnapshot` (migration `2026_08_18_000002_create_insight_snapshots_table.php`) is that frozen copy — `panel_key`, `scope` (`week`/`month`), `title`, `period_label`, an optional `caption`, the actual `rows` (`{label, detail}[]`, JSON-cast), and an optional client `note`. A `Share` row with `shareable_type = InsightSnapshot::class` is created in the same request, granting visibility; `InsightSnapshot::share(): MorphOne` reflects that in practice a snapshot is only ever shared once (a re-share creates a new snapshot + new Share, never reuses one).

**Audience is implicit, not stored per-share.** `Share` has no grantee column — visibility is resolved dynamically against whoever the client's *current* linked therapist is (`TherapistClient`, one-active-link-at-a-time, same rule §2 describes), the same "always resolve against the live link, never a snapshot taken at share-time" pattern `CrisisThreadController` already uses. If a client switches therapists, old shares stop being visible to the old therapist and are **not** retroactively visible to the new one (`forClient()` checks the *current* link, but a previous therapist's `Share` rows were only ever queryable by them in the first place — nothing hands them to a successor).

**Revoke, not delete.** `SharedInsightController::destroy()` sets `revoked_at`; the row stays so the client's own history (`index()`) still shows "you shared this, then took it back." A revoked share is invisible to the therapist immediately and completely — `forClient()` filters `whereNull('revoked_at')`, so nothing marks it as "withdrawn" on their side, it's simply gone.

**API surface:**
```
POST   /api/shared-insights                     client — freeze + share one panel (requires an active therapist link)
GET    /api/shared-insights                      client — own share history, including revoked
DELETE /api/shared-insights/{share}               client — revoke (must own it)
GET    /api/shared-insights/client/{clientId}     therapist — one linked client's ACTIVE shares only
```
No Policy layer, matching every other controller — ownership/role checks inline (`SharedInsightController`, same style as `TherapistLinkController`).

**Frontend.** `Dashboard.vue`'s six weekly panels (mood ring, feelings, what's-helping, behaviors pie, what's-weighing-on-you, needs) and `MonthlyDashboard.vue`'s six trend panels (rendered from one `v-for`, so a single insertion covers all of them) each got a small `share` button in a new `.panel-head` wrapper next to the title, matching the user's own framing ("a little button in the upper side"). Clicking it opens one shared confirm overlay (not six duplicated popovers) showing the period, an optional note field, and a share/cancel pair — this codebase has no shared-component convention (every view is self-contained per `spa/src/views/`), so the overlay is written once per file rather than extracted. An already-shared panel for the current period shows "✓ shared" instead of "share," backed by a `GET /api/shared-insights` fetch on mount.

New `SharedInsights.vue` (`/therapist/insights`) mirrors `CrisisThread.vue`'s role-branch + `?client_id=`(`+ ?name=` for the header, since `forClient()` itself doesn't return the client's name) query-param handoff: a client sees their full history (active cards, then a greyed "unshared" section) with an unshare button per card; a therapist sees one linked client's active shares, read-only, each showing the frozen rows/caption/note. Linked from `Therapist.vue` on both branches — a "shared insights →" link per client row (therapist side), a "what you've shared →" button next to "open conversation →" (client side).

**Verification.** All new/edited PHP files checked with the heredoc-aware Python brace/paren/bracket balance checker (sanity-checked against a deliberately broken file first, same as every backend change this project). The full store → index → revoke → forClient lifecycle was simulated against a scratch copy of the live SQLite file (`/tmp/scratch_shared_insights.sqlite`, using this app's real `users`/`therapist_client` rows) — asserted a share appears in `forClient()` before revoke, disappears immediately after, and still appears (with `revoked_at` set) in the client's own `index()`. All new/edited Vue files checked with `@vue/compiler-sfc`'s `parse`/`compileScript`/`compileTemplate`; `router/index.js` checked with `node --check`. The migration was applied directly to the live SQLite file (no PHP runtime available in this environment) and recorded in Laravel's own `migrations` table, same as every other migration this session.

**What this deliberately does not do.** No push/email notification when a client shares something — same "always live, check when you check" pattern as the rest of this app (§4's list applies here too). No granular field-level redaction inside a panel (e.g. hiding one row out of five) — a share is the whole panel or nothing, matching the coarser "per-item" grain the original spec describes rather than per-row. No re-share/edit of an existing snapshot — unshare and share again if the data's moved on.

## 9. Therapist-assigned tasks (2026-08-18)

**User's request, verbatim:** *"i want to add tasks if he wants to give them to it's patient and the patient cross them."*

New `AssignedTask` model/table (migration `2026_08_18_000003_create_assigned_tasks_table.php`) — `therapist_id`, `client_id`, `title`, optional `instructions`, optional `due_date` (plain `Y-m-d` string, deliberately uncast, same discipline `DailyReview`'s docblock argues for even though nothing here does a raw-array search on it), and `completed_at`. A therapist assigns; the client checks it off — `TaskController::toggleComplete()` flips `completed_at` rather than one-way setting it, so an accidental tap is undoable, matching this app's habit of never making a confirm-style action a one-shot trap.

**Scoping mirrors §8's share-to-therapist rules exactly, on purpose** — same shape of problem (something crossing the therapist↔client boundary), same answer: `store()` requires an active `TherapistClient` link before a task can be created; `forClient()` (therapist's view of one client's tasks) is scoped to `WHERE therapist_id = <me> AND client_id = <them>` plus a currently-active-link check, so a therapist loses visibility into their own old tasks once unlinked, and never sees another therapist's tasks for a client they both happened to have. The client's own `index()` is the one asymmetry: it returns *every* task ever assigned to them regardless of current link status, same "history stays visible even after the relationship changes" rule `CrisisThreadController` established for old messages.

**API surface:**
```
POST   /api/tasks                      therapist — assign (requires an active link to client_id)
GET    /api/tasks                      client — every task ever assigned to them, incomplete-first
GET    /api/tasks/client/{clientId}    therapist — tasks THEY assigned to one currently-linked client
PATCH  /api/tasks/{task}/complete      client — toggle done/not-done
DELETE /api/tasks/{task}               therapist — remove one they created
```
No edit endpoint by design (v1 scope) — delete and re-assign covers a mistake without a second code path that sets the same fields `store()` does. No Policy layer, ownership checks inline, same as everything else in this app.

**Frontend.** New `Tasks.vue` (`/therapist/tasks`) — same role-branch + `?client_id=`(`&name=`) handoff as `SharedInsights.vue`. Therapist branch adds a small assign form (title, optional instructions, optional due date) above the list of tasks they've given this client, each removable. Client branch lists every task, split into a pending group (oldest due date first, overdue ones bordered in `--ochre`) and a collapsed "done" group below, each pending row a checkbox the client taps to cross it off. `Dashboard.vue`'s header bar gets a small pill — `{n} tasks` in `--accent`, only rendered when `n > 0` — linking straight to `/therapist/tasks`, since a task nobody notices never gets crossed off; this was the one addition beyond exactly what was asked, chosen because §8's share buttons already taught the same lesson (a feature only used from a subpage two clicks deep gets forgotten).

**Verification.** Same discipline as §8 — PHP balance-checked (all new/edited files), a full store → forClient → index → toggle(on) → toggle(off) → destroy lifecycle simulated against a scratch copy of the live SQLite file using this app's real `therapist_client` row, plus an explicit check that a task's ownership WHERE clause matches zero rows for a therapist_id that isn't the assigning one (guards the delete/forClient scoping isn't accidentally permissive). All new/edited Vue files checked with `@vue/compiler-sfc`; `router/index.js` checked with `node --check`. Migration applied directly to the live SQLite file and recorded in `migrations`, no PHP runtime available in this environment.

**Not built (v1 scope, noted so it isn't mistaken for an oversight):** no recurring tasks, no requiring a written reflection to close one out, no therapist edit-in-place, no due-date reminder of any kind (this app has no notification system at all — see §4's list, same constraint applies here).

## 10. Scheduled sessions (2026-08-18)

**User's request, verbatim:** *"the therapist page looks empty should we add calendar for it to check when is the session and befor a day a notification to checkthe in between progress."* Resolves the "Live trend view"-adjacent gap `therapist-roadmap.md` had flagged as "no concept of a 'session' exists anywhere in this app yet."

New `TherapySession` model/table (migration `2026_08_18_000004_create_therapy_sessions_table.php`) — `therapist_id`, `client_id`, `scheduled_at` (a real datetime, unlike `AssignedTask.due_date`, since a session has a time of day and this app's `.env` sets `SESSION_DRIVER=database`, which already owns a table literally named `sessions` for Laravel's own session storage — confirmed empty-of-collision before naming this `therapy_sessions`), optional `notes`. `scheduled_at` is cast `'datetime'` — safe here, unlike `DailyReview`'s infamous `'date'` cast bug, because nothing does a raw-array `where()` search keyed on it; every lookup goes through the primary key or `therapist_id`/`client_id`.

**"A day-before notification" is honestly an in-app highlight, not a real notification.** This app has no email/push/SMS delivery anywhere (§4's list). `TherapySession::is_soon` (appended, computed live off `Carbon::now()`, never stored) is true when a session is in the future and within 24 hours — surfaced as a highlighted card the moment either side opens `Sessions.vue`, `Therapist.vue`, or `Dashboard.vue`, never before that. For the therapist it reads "worth a look before you meet" and links straight to that client's shared insights and tasks — the actual "check the in-between progress" the request asked for, just pull-based instead of push-based, same "always live, check when you check" pattern every other reminder in this app already uses (daily-review banner, task pill, gentle notes).

**Scoping mirrors §8/§9 exactly.** `store()`/`update()`/`destroy()` are therapist-only, require ownership (`therapist_id` matches) plus, for `store()`, an active `TherapistClient` link. `forClient()` is scoped to sessions THEY scheduled with a client they're CURRENTLY linked to. The one deliberate difference from `AssignedTask`: `update()` exists here (reschedule is a real, expected calendar action) where tasks have none (delete+recreate was judged good enough there) — losing an already-written session note to a forced delete would be a real annoyance a task's due date isn't.

**`GET /api/sessions` is role-aware**, a new pattern for this feature set (§8/§9's client-only `index()` doesn't have a therapist branch). A client gets every session ever scheduled with them, full history regardless of current link status, same asymmetry as tasks/shares. A therapist gets every session they scheduled across every client they're CURRENTLY linked to, in one call — needed so `Therapist.vue`'s landing page could show a real "next session" summary without firing `forClient()` once per client row. Verified via scratch simulation that a session left over from a client who has since unlinked (`client_id` no longer in `therapist_client`) is correctly excluded from this aggregate view.

**API surface:**
```
POST   /api/sessions                      therapist — schedule (requires an active link to client_id)
PATCH  /api/sessions/{session}            therapist — reschedule / edit notes (must own it)
DELETE /api/sessions/{session}            therapist — cancel (must own it)
GET    /api/sessions                      role-aware: client's full history, or therapist's across all currently-linked clients
GET    /api/sessions/client/{clientId}    therapist — sessions THEY scheduled with one currently-linked client
```

**Frontend — this was the actual fix for "the page looks empty."** New `Sessions.vue` (`/therapist/sessions`) is the full CRUD surface, same role-branch + `?client_id=`(`&name=`) handoff as `Tasks.vue`/`SharedInsights.vue`: a schedule form (`datetime-local` + optional notes) on the therapist side, inline reschedule per row, upcoming/past split. ## 13. Pre-session briefs (2026-08-19)

## 14. Live trend view (2026-08-19)

Gives a therapist a continuous, live view of a linked client's monthly trend data — without touching the client's own `MonthlyDashboard.vue`, which remains their personal journaling view.

**Consent gate.** Migration `2026_08_19_000003_add_live_trends_to_therapist_client_table.php` adds `live_trends_enabled` (boolean, default false) directly to the `therapist_client` pivot. **Frontend.** New `ClientTrends.vue` (`/therapist/trends`) — built from scratch in TherapistDashboard.vue's practice-management language (stat strip, card grid, chip buttons, `--shadow` depth, accent-tinted headers), not MonthlyDashboard.vue's personal-journaling framing. Same underlying SVG trend charts and per-panel independent zoom, same categorical 8-color palette — just different surrounding UI. ## 16. Shared insights: comparison context (2026-08-19)

**User's request, verbatim:** *"when it comes to shared insigntss how do we make the more suitable and helpful to the therapist not just copy paste."* Discussed a few directions in chat (comparison against baseline, comparison against the client's last share of the same panel, therapist-authored notes, visual flagging of what's elevated) and built the highest-value one: comparison against the client's own baseline.

**What was actually "copy paste" before.** `InsightSnapshot.rows` were the exact `{label, detail}` pairs the client's own weekly dashboard panel already showed — a single frozen number (e.g. "sadness — 40%") with nothing to compare it against. A therapist had no way to tell whether that was a spike or nothing new without already knowing this client well.

**`SharedInsightController::attachComparisonContext()`**, called from `store()` only when `scope === 'week'` and `panel_key` is a mapped tag-breakdown panel (`emotion_breakdown`, `stressor_breakdown`, `protective_factor_breakdown`, `behavior_breakdown`, `need_breakdown`, `thinking_pattern_breakdown` — `PANEL_FIELD_MAP` mirrors the `{column, labelKey, weightKey}` triples `WeeklyReflectionController::generateContent()` already uses per field). `mood` (not a tag list) and `thread`/`month`-scope shares (month-scope already carries trend framing from `MonthlyDashboardController`) are deliberately left out.

For each row it **recomputes both sides itself** rather than trusting the frontend's `detail` string (free-form display text, not a parseable number): the current week's presence rate and a rate over the `BASELINE_WEEKS` (6) weeks immediately before it, both via the existing `TagBreakdownService::breakdown()` with the same reliability filter (`extraction_confidence === null || >= 0.4`) and the same Monday-start week boundary `WeeklyReflectionController` uses — so "this week" here means the same thing it meant on the screen the client just shared from. Looked up with a high `$limit` (50) rather than the usual top-5, since this needs to find whichever specific labels are already in the client's rows, not rank them.

Each row gets a `context` string appended directly into the stored `rows` array (no migration — `rows` is already array-cast): `"new this week — hasn't shown up in the prior 6 weeks."` when the baseline rate is zero, `"up from ~X% typically over the past 6 weeks."` / `"down from ~X% typically..."` when the delta crosses `DELTA_THRESHOLD` (0.10 — the same up/down threshold `MonthlyDashboardController::directionFor()` already uses, not a second invented number), or `"about typical for you (~X%...)."` otherwise. Silently skips a row (no `context` added) when the client has fewer than `MIN_BASELINE_ENTRIES` (2) reliable analyses in the baseline window, or when a row's label doesn't turn up in the server's own recomputed current-week breakdown at all — never fabricates a comparison from a label it can't verify.

**Frontend.** `SharedInsights.vue` renders `row.context` as a small accent-tinted secondary line under the existing label/detail row, only when present — visually distinct from the client's own original panel content, so it reads as therapist-facing added context rather than something the client wrote.

**Verified against real demo data** via a scratch copy of the live SQLite file, replicating the exact PHP query/aggregation logic in Python: for the seeded client, sadness went from an 8% baseline (66 reliable analyses over the prior 6 weeks) to 38% this week (16 reliable analyses) — correctly flagged `"up from ~8% typically..."`. Two newly-appearing emotions (annoyance, embarrassment) correctly flagged `"new this week"`.

**Not built.** No comparison for `mood`, thread-scoped, or month-scoped shares. No therapist-authored annotation layer (a separate idea from the same discussion, not started). No link from a row to the actual entries behind it — deliberately out of scope, see the chat discussion: that's a bigger consent step (raw entry text vs. an aggregate stat) than what sharing a panel currently means.

## 18. Shared insights round 2: trajectory, private note, row flag (2026-08-19)

Follow-up to §16, building the remaining 3 items from the original brainstorm (comparison-against-last-share, therapist-authored note, visual flagging).
